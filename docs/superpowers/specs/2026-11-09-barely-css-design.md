## Intent

Pico CSS is no longer maintained. barely-css replaces it for the owner and for people like them: a single stylesheet that makes plain semantic HTML look considered, with no classes, no JavaScript, and no build step.

The owner's main use case shapes the design. They write course content as raw HTML for Canvas (Canvas does not accept Markdown) and paste only what is inside `<body>`. Canvas applies its own styling. Locally, they link the framework so they never review unstyled pages. This means:

- The framework's value is in **local authoring and standalone sites**. It does not need to style anything inside Canvas, and it must not try to.
- **Body markup must stay portable.** If the framework requires a class or wrapper element, the HTML no longer reads cleanly under another stylesheet. v1 therefore never requires classes, wrappers, or attributes for its baseline.

Other target uses: blogs, documentation, knowledge bases, educational projects, prototypes and MVPs, server-rendered apps (Flask, Django), HTML generated by AI, and accessibility-first projects.

## What the owner wants fixed compared to Pico

1. **Customization through custom properties.** Pico hard-codes many values, so you end up overriding selectors. In barely-css nearly every visual decision (color, font, size, spacing, radius, border, shadow, control dimensions) reads from a custom property. Overriding a token in `:root`, or on any element, must be enough.
2. **Page-level spacing.** With Pico the owner kept adding padding to the top of each page because the first element sat too close to the top edge. They also kept adding a custom container class to get side padding. barely-css gives the page's main regions generous block and inline spacing by default, with no class, controlled by two tokens (for example `--barely-page-padding-block` and `--barely-page-padding-inline`). Both are fluid: each defaults to a `clamp()` of the viewport width, so the spacing is tighter on phones and roomier on large screens. Overriding either token replaces the fluid default with a fixed value or a different `clamp()`.

Pico's vertical rhythm inside the page was fine. Keep a similar density and don't loosen it.

## Goals (v1)

- A classless semantic baseline for the **content side**: typography, page structure, navigation, tables, code, media, forms, and native interactive elements.
- A token-driven design: semantic tokens (such as `--barely-color-text`, `--barely-color-surface`, `--barely-color-primary`) that can be overridden at runtime without recompiling.
- Built-in light and dark themes that follow the system preference, with explicit overrides and nested theme scopes.
- Accessibility built into the baseline.
- Distribution as a single CSS file through a CDN, as an npm package, and as a plain file to download.
- A demo page with a full set of semantic HTML that shows every styled element in both themes.

## Non-goals

- **Email templates.** These were considered and dropped. No inlining, fallbacks, or email-client support.
- **App and dashboard UI.** Sidebar layouts, cards, badges, and dense data views come in a later version.
- **The class-light layer** (`.container`, `.grid`, and similar), which is reserved for v2. When v2 adds `.container`, it must reuse `--barely-page-padding-inline` and `--barely-content-width`, not define its own values. A `.container` nested inside a region that already has page padding must not add its own padding or width cap on top.
- **Component classes**, which come after v2.
- **Styling content inside Canvas** or any host that strips `<link>` and `<style>`.
- **Older browsers.** Only current evergreen browsers are supported, with no fallbacks for older ones.
- **A JavaScript dependency**, or a build step required to use the framework.

## Anti-goals

Even if everything else works, the project fails if the result looks like unstyled browser defaults:

- Times New Roman, Arial, or Helvetica as the visible typeface.
- Pure black (`#000`) text on pure white (`#fff`), or the reverse in dark mode. Use softly tinted neutrals instead.
- Tight paragraph line height. Body copy needs generous line height (around 1.6, **builder's call** on the exact value).

## Decided constraints

- **No classes are needed** for anything in v1.
- **Every public custom property has a prefix,** so it can't collide with a site's own variables. The prefix is `--barely-`, as in `--barely-color-primary`. The exact prefix was a **(builder's call)**. Internal helper properties should use a separate private prefix, such as `--_barely-`, so they stay out of the documented API.
- **Plain CSS is the source.** No Sass, PostCSS, or other preprocessor is required to read or edit the source. Shipping a minified copy is fine.
- **Evergreen browsers only.** Use cascade layers, nesting, `:has()`, `:where()` and `:is()`, `oklch()`, `color-scheme`, logical properties, and container queries freely. Document the support policy in one sentence.
- **Fonts:**
  - Body and headings use a system sans-serif stack, exposed as `--barely-font-sans`.
  - Code uses a system monospace stack, exposed as `--barely-font-mono`.
  - No web fonts are loaded.
  - The sans stack must resolve to the platform UI font (`system-ui` and its equivalents). It must not fall back to Arial or Helvetica on common platforms.
- **Distribution:**
  - A CDN link through **jsDelivr**, which serves the npm package automatically. It is the only CDN the docs mention. unpkg also serves the package, but it runs on a single provider and has had outages, so it isn't documented. cdnjs can be added later if people ask for it.
  - An npm package.
  - A file that can be downloaded and linked from disk, which must work over `file://`.
- **Page spacing** is tokenized, fluid, and generous at the top and on the sides, as described above.

## The baseline (v1 scope)

Elements to style without classes:

| Category    | Elements |
| ----------- | -------- |
| Typography  | `h1`–`h6`, `p`, `ul`, `ol`, `dl`, `blockquote`, `hr`, `a`, `strong`, `em`, `small`, `mark`, `abbr`, `sub`, `sup`, `del`, `ins` |
| Code        | `pre`, `code`, `kbd`, `samp` |
| Structure   | `header`, `main`, `footer`, `section`, `article`, `aside` |
| Navigation  | `nav` in the site masthead (horizontal link list), breadcrumbs using `nav[aria-label="breadcrumb" i]`. See the navigation rule below. |
| Tables      | `table`, `caption`, `thead`, `tbody`, `tfoot`, `th`, `td` |
| Media       | `img`, `figure`, `figcaption`, `video`, `audio`, `iframe` (responsive, never overflowing) |
| Forms       | `label`, `input` (text-like, checkbox, radio, range, file, search, date and time, color), `select`, `textarea`, `fieldset`, `legend`, `button` |
| Interactive | `details` and `summary`, `dialog`, `progress`, `meter`, popovers (`[popover]`) |

Behavior rules:

- **Page layout without classes.** See [Page layout](#page-layout) below.
- **Context-aware structure.** The site header and footer (`body > header`, `body > footer`) get masthead treatment. A `header` or `footer` inside `article` or `section` must not, and gets restrained styling instead.
- **Navigation layout is scoped to the masthead.** A layout is never inferred from the presence of `<nav>` alone.
  - Only `body > header nav > ul` is laid out horizontally. The descendant combinator lets the masthead wrap the `nav` in a `div`, which generated HTML often does, while keeping the rule inside the masthead.
  - Only the nav's top-level lists are affected. A nested `ul` inside a list item, such as a submenu, stays vertical. There are no dropdowns, because CSS can't provide that behavior.
  - Pico's two-list pattern keeps working. In `<nav><ul>…brand…</ul><ul>…links…</ul></nav>`, the first list sits at the start edge and the second at the end edge. A single list runs horizontally from the start edge.
  - Rows wrap at narrow widths and never scroll horizontally. There is no hamburger menu.
  - Every other `nav`, including one in `body > footer`, an `aside`, `main`, or an `article`, is styled as an ordinary list.
  - Breadcrumbs are the one exception. `nav[aria-label="breadcrumb" i]` gets breadcrumb styling wherever it appears. The `i` flag makes the match case-insensitive.
- **Tables.** Basic content tables are in v1. Dense data views are deferred (see Non-goals).
  - **Semantics come first.** The `table` element keeps its native `display: table`. It is never set to `display: block` to make it scroll, because some browser and screen reader pairs, notably Safari with VoiceOver, have dropped table semantics when that is done.
  - **Most tables fit by wrapping.** Cells wrap long content, including long words and URLs (`overflow-wrap: break-word`), so most tables fit the content width with no help.
  - **Optional scroll wrapper.** For a table that is truly too wide, the README documents an optional wrapper that barely-css styles if it is present:
    ```html
    <div role="region" tabindex="0" aria-label="Grades by week">
      <table>…</table>
    </div>
    ```
    The selector is `div[role="region"][tabindex]:has(> table)`. The wrapper gets `overflow-x: auto` and a visible `:focus-visible` outline, so keyboard users can scroll it. The wrapper is never required, so the no-wrappers rule for the baseline still holds, and the markup still reads cleanly under another stylesheet.
  - **Accepted exception.** A wide table without the wrapper may make the page scroll horizontally. This is the only place the baseline allows that, and the README says so next to the wrapper example.
  - **Smaller defaults (builder's call):**
    - `caption` sits above the table, start-aligned.
    - `th` is start-aligned and bold.
    - `thead` gets a bottom rule in `border-strong`. Rows are separated by `border`.
    - `tbody` rows are striped with `surface`.
    - `tfoot` gets a top rule.
    - Tables use `font-variant-numeric: tabular-nums` so digits line up. Columns are not right-aligned, because CSS can't tell which columns hold numbers without a class.
- **Fluid type.** Headings scale with `clamp()`. The scale comes from tokens.
- **Forms.** See [Forms](#forms) below.
- **No implied behavior.** CSS must not fake interactivity it can't provide.

### Page layout

Four tokens control the page, and each has one job:

| Token | Controls | Default **(builder's call** on exact values**)** |
| ----- | -------- | ------- |
| `--barely-content-width` | Maximum width of the content inside each page region, padding excluded | About `72rem` |
| `--barely-reading-width` | Maximum width of prose | About `70ch` |
| `--barely-page-padding-inline` | Minimum space between content and the viewport edge. This does the job the owner's container class did under Pico. | `clamp()` scaled with viewport width, about `1rem` to `2rem` |
| `--barely-page-padding-block` | Vertical spacing of the page | `clamp()` scaled with viewport width, about `2rem` to `4rem` |

Rules:

- **Box sizing.** The reset layer sets `border-box` with the inheritable pattern, so padding and maximum widths combine predictably and an embedded widget can still opt out:
  ```css
  html { box-sizing: border-box; }
  *, ::before, ::after { box-sizing: inherit; }
  ```
- **Page regions.** Every direct child of `body` is a page region, except `script`, `style`, `template`, and `dialog`. That includes `header`, `main`, and `footer`, and also any content placed directly in `body` on pages that have no `main`.
- **Regions span the viewport and narrow their content with padding.** A region is never given a `max-width`. Instead it gets:
  ```css
  padding-inline: max(
    var(--barely-page-padding-inline),
    (100% - var(--barely-content-width)) / 2
  );
  ```
  On narrow screens the padding equals the edge token. On wide screens it grows so the content stays centered at `--barely-content-width`. Because the region itself is full width, its background and borders reach both viewport edges while its content lines up with every other region. This is how the masthead `header` and `footer` get edge-to-edge backgrounds with no wrapper, and why the layout can't cause horizontal scroll.
- **Block spacing.** `body > main` gets `padding-block: var(--barely-page-padding-block)`. A page with no `main` (detected with `:has()`) gets that padding on `body` instead. The masthead `header` and `footer` get tighter block padding derived from the same token **(builder's call)**.
- **Reading width.** `p`, `ul`, `ol`, `dl`, `blockquote`, `h1`–`h6`, `figcaption`, and `form` get `max-inline-size: var(--barely-reading-width)`. Tables, `pre`, `figure`, and media use the full content width.
- **Prose is start-aligned, not centered.** When the content width is wider than the reading width, prose sits at the start edge of the content region, lined up with wider tables, code blocks, and the header content. The extra space falls on the end side. In RTL, start is the right edge.
- **Only page regions.** A `header` or `footer` inside `article` or `section` gets none of this. It follows the context-aware structure rule above.

### Forms

The approved preview is at https://claude.ai/artifact/UEC92afWaKez4QYLtMtGpV. These rules were measured with Playwright in Chromium, Firefox, and WebKit.

**Form tokens** (defaults are a **builder's call**; the names are decided):

| Token | Controls | Preview default |
| ----- | -------- | --------------- |
| `--barely-control-height` | Minimum height of text-like controls and buttons. Never a fixed height, so text can grow at 200% zoom. | `2.75rem` |
| `--barely-control-padding-block` | Vertical padding inside controls | `0.5rem` |
| `--barely-control-padding-inline` | Horizontal padding inside controls | `0.875rem` |
| `--barely-control-radius` | Corner radius of controls and buttons | `0.375rem` |
| `--barely-control-border-width` | Normal control border | `1px` |
| `--barely-control-border-width-invalid` | Border in the invalid state | `2px` |
| `--barely-control-background` | Fill of text-like controls | `var(--barely-color-background)` |
| `--barely-check-size` | Checkbox and radio size. The switch is 1.9 times as wide. | `1.25rem` |
| `--barely-focus-ring-width` | Focus outline width | `2px` |
| `--barely-focus-ring-offset` | Focus outline offset | `2px` |
| `--barely-form-gap` | Space between fields | `1.125rem` |

**Rules:**

- **Width.** `form` is capped at `--barely-reading-width`, so single-line inputs don't stretch across the full content width.
- **Labels are always `display: block`, never grid or flex.** The preview first used a grid label, and Playwright measurements showed two bugs. First, inline elements in the label text, such as `<abbr>`, `<strong>`, or `<span>`, became separate grid rows and broke the text onto several lines. Second, when a label was stretched to match a taller neighbor in a row, its control stretched with it (58px instead of 44px). With a block label:
  - The control inside a wrapping label is `display: block` with a small top margin, so the label text stacks above it.
  - A `small` directly after the control is helper text: `display: block`, muted, and smaller. Authors link it with `aria-describedby`.
- **Text-like controls** are selected by exclusion: every `input` except `checkbox`, `radio`, `range`, `file`, `color`, `submit`, `reset`, `button`, `image`, and `hidden`, plus `select` and `textarea`. Unknown or future input types get text styling automatically. They are full width, use the control tokens, and use `appearance: none`.
  - Date and time inputs keep the native picker. `color-scheme` makes it match the theme. Digits are tabular.
  - `select` draws its chevron with gradients in `currentColor`, so it follows the text token, and moves the chevron to the start side in RTL.
  - `textarea` has a minimum height of about 6.5rem and resizes vertically only.
- **Checkbox, radio, and switch** are drawn with `appearance: none`, so every color comes from tokens.
  - The check mark is a CSS mask filled with `on-primary`. `:indeterminate` shows a dash. The radio dot and the switch knob are `::before` pseudo-elements. Playwright confirmed these render in Chromium, Firefox, and WebKit.
  - Their label is a block with a hanging indent. The control sits beside the text, wrapped lines align with the text rather than under the control, and inline content flows normally. The control uses `vertical-align: middle` so the checked mark can't shift the line. At line height 1.6 each row is at least 24px tall, meeting the 2.5.8 target size.
  - A switch is written as `input[type="checkbox"][role="switch"]`, following Pico's convention so existing markup keeps working. Its knob mirrors in RTL.
  - In `forced-colors` mode they fall back to `appearance: auto`.
- **Range** stays native, tinted with `accent-color: var(--barely-color-primary)`. It keeps platform keyboard and screen reader behavior, and a custom track can't show progress in Chromium or WebKit without script.
- **File** inputs get a dashed border. `::file-selector-button` uses the secondary button style.
- **Color** inputs are a swatch at control height.
- **Fieldset** is borderless, and its `legend` is styled like a label.
- **Buttons.** `button`, `input[type="submit"]`, and `input[type="button"]` are primary, matching Pico. `input[type="reset"]` is secondary, because reset destroys input and shouldn't look like the main action. A classless stylesheet can't tell which button is the main action, so this is the whole hierarchy in v1. Buttons share the control height and radius, so a button lines up beside an input.
- **States:**
  - **Focus:** a `:focus-visible` outline of `--barely-focus-ring-width` in `primary` at `--barely-focus-ring-offset`. Text-like controls also change their border to `primary`. The outline is never removed.
  - **Disabled:** surface fill, muted text, `border` color, and a not-allowed cursor. The label text is muted too, using `label:has(> :disabled)`.
  - **Read-only:** matched with `[readonly]`, not `:read-only`, because `:read-only` also matches checkboxes. Surface fill and a dashed border, so it differs from disabled by more than color.
  - **Invalid:** `:user-invalid` (native, after interaction or a submit attempt) or `[aria-invalid="true"]` (errors rendered by the server, for example Flask or Django, visible on page load). The border turns `danger` and widens to `--barely-control-border-width-invalid`. A `small` right after the control turns `danger` and gets an icon. Color is never the only signal.
  - **Valid:** shown only for an explicit `[aria-invalid="false"]`, with a `success` border and a check icon on the following `small`. `:user-valid` is not styled, so fields don't turn green as people type.
  - **Required:** CSS adds no asterisk. Native `required` is already announced, and screen readers read a CSS-generated asterisk inconsistently. Authors who want one write it into the label.
- **Validation** is native only. barely-css never needs script to show a state.

## Theming

- Light and dark themes follow `prefers-color-scheme` by default.
- `data-theme="light"` or `data-theme="dark"` on `<html>` forces a theme for the whole page. On any other element, it creates a nested scope, such as a light panel inside a dark page.
- Every theme sets `color-scheme`, so native controls and scrollbars match.
- Suggested approach **(builder's call)**:
  - Define the color tokens with `light-dark()`.
  - Have `data-theme` set only the `color-scheme` property.
  - With this approach, nested scopes need no duplicated token blocks.
- Colors use `oklch()`. Neutrals are slightly tinted toward the primary hue. The default primary is blue at hue 250–255.

### Color tokens

These values were approved with the owner on 2026-11-10. Once the build begins, `tokens.css` becomes the source of truth for the values. This spec then keeps the names and roles, so the numbers aren't kept in two places.

| Token | Role | Light | Dark |
| ----- | ---- | ----- | ---- |
| `--barely-color-background` | Page background | `oklch(0.985 0.004 250)` | `oklch(0.19 0.012 250)` |
| `--barely-color-surface` | Code, table stripes, secondary buttons | `oklch(0.955 0.008 250)` | `oklch(0.23 0.014 250)` |
| `--barely-color-border` | Rules, `hr`, decorative edges | `oklch(0.89 0.012 250)` | `oklch(0.33 0.016 250)` |
| `--barely-color-border-strong` | Form control outlines | `oklch(0.6 0.02 250)` | `oklch(0.58 0.02 250)` |

| `--barely-color-primary` | Links, buttons, focus ring | `oklch(0.5 0.16 255)` | `oklch(0.75 0.12 250)` |
| `--barely-color-primary-hover` | Hover and active states | `oklch(0.43 0.15 255)` | `oklch(0.82 0.1 250)` |

| `--barely-color-success` | Valid state, confirmations | `oklch(0.5 0.12 150)` | `oklch(0.76 0.14 150)` |
| `--barely-color-warning` | Cautions | `oklch(0.53 0.12 65)` | `oklch(0.8 0.13 75)` |
| `--barely-color-danger` | Invalid state, errors | `oklch(0.52 0.18 27)` | `oklch(0.73 0.15 25)` |

Rules for these tokens:

- **Two border tokens.** `border` is decorative and may be low contrast. `border-strong` outlines form controls and must reach 3:1 against `background` and `surface` (WCAG 1.4.11).
- **The focus ring uses `primary`** at 2px with an offset. There is no separate focus token.
- **The dark theme is not an inversion.** Its background stays above near-black, its text stays below white, and `primary` gets lighter and less saturated.
- **Status hues stay the same across themes.** Only lightness and chroma change.
- **Contrast pairs that must pass WCAG 2.2 AA in both themes,** checked automatically (see Deliverables):

  | Foreground | Background | Minimum |
  | ---------- | ---------- | ------- |
  | `text` | `background`, `surface`, `mark` | 4.5:1 |
  | `text-muted` | `background`, `surface` | 4.5:1 |
  | `primary` | `background` | 4.5:1 |
  | `on-primary` | `primary`, `primary-hover` | 4.5:1 |
  | `success`, `warning`, `danger` | `background` | 4.5:1 |
  | `border-strong` | `background`, `surface` | 3:1 |

  All pairs pass with the values above. The lowest ratio is `border-strong` on `surface` in the light theme, at 3.46:1.

## Architecture

- Layer order, declared once at the top:
  ```css
  @layer reset, tokens, base, layout, components, utilities, overrides;
  ```
  v1 fills only `reset`, `tokens`, and `base`. The other layer names are declared now so v2 can add to them without reordering. Styles a user writes outside any layer beat all framework layers automatically.
- Element selectors are wrapped in `:where()` wherever possible, which keeps their specificity at or near zero.
- Logical properties are used everywhere (`margin-block`, `padding-inline`, `inset-inline-start`) so RTL layouts work.
- Source layout **(builder's call)**: one file per area, such as `tokens.css`, `typography.css`, and `forms.css`, concatenated into a single distributable file. The concatenation script exists only for maintainers. Users never need it.

## Accessibility requirements

- Text and UI elements meet WCAG 2.2 AA contrast in both themes.
- Focus is always visible through `:focus-visible` with a tokenized outline. The outline is never removed.
- Interactive targets are at least 24×24 CSS px (WCAG 2.2, criterion 2.5.8).
- `prefers-reduced-motion` turns off non-essential transitions.
- `forced-colors` mode keeps controls, focus rings, and borders visible, using system colors where needed.
- Pages stay usable at 200% zoom and with enlarged text. Avoid fixed heights on text containers.
- Status (error, success) is never conveyed by color alone.

## Release criteria

`1.0.0` is published only when all of the following are true. Until then, releases are `1.0.0-beta.N`.

- Every element in the baseline table is styled and appears on the demo page in both themes. The demo also includes the nested theme scope and the RTL section.
- The axe scan reports no violations on the demo page, and every contrast pair under Color tokens passes in both themes.
- Both dist files are current with `src/`, and the README covers everything listed under Deliverables.
- The Playwright suite passes in Chromium, Firefox, and WebKit, including the `file://` check. The demo page has also been checked by hand in current Chrome, Firefox, and Safari.
- At least one of the owner's real course pages renders correctly with only the stylesheet changed from Pico to barely-css, with no classes or wrappers added to the markup.

Build order and milestones belong in the implementation plan, not in this spec.

## Versioning and changelog

barely-css follows semantic versioning. For a stylesheet, a version change means:

- **Major:**
  - A public `--barely-*` token is renamed or removed.
  - An element the baseline covered is no longer styled.
  - The layer order changes.
  - Markup that worked before needs to change.
- **Minor:**
  - New tokens or newly styled elements.
  - Deliberate visual changes to defaults, such as a new spacing or color value. These are not breaking, because overriding the token restores the old look. The changelog lists each one under its own "Changed defaults" heading so users can find them.
- **Patch:** Bug fixes that restore the intended look, such as a contrast failure, an overflow, or a browser quirk.
- **Private `--_barely-*` properties** can change in any release and are never covered by the policy.

The changelog plan:

- `CHANGELOG.md` uses the [Keep a Changelog](https://keepachangelog.com) format.
- It is created when building starts, with an `Unreleased` section that gets a line for each meaningful change as the work happens.
- The first published version is `1.0.0`, which matches the `@1` CDN link in the README. A trial period, if wanted, uses `1.0.0-beta.N` pre-releases, which jsDelivr's `@1` link does not pick up.

## Deliverables

1. The CSS source and two distributable files, both built from the same concatenation of `src/` so they can't drift apart:
   - `dist/barely.css` is unminified. It keeps comments, especially token descriptions and layer headers, because readers use it to learn the token API, to edit a downloaded copy, and to debug in devtools.
   - `dist/barely.min.css` is minified. It strips all comments except a one-line banner with the license and version.
   - No source maps. The unminified file is effectively the source.
   - The `package.json` `style` field and default `exports` entry point to `barely.css`, since bundlers minify on their own. `barely.min.css` is available as an explicit subpath export.
   - The README's CDN snippet links `barely.min.css`. The download instructions point to `barely.css`.
   - A check fails if either dist file is out of date with `src/`.
2. `package.json` set up for npm publishing, so the file is available from jsDelivr. **(builder's call)**:
   - The package name is `barely-css`, taken from the project folder. Check that it's available before publishing.
   - The license is MIT.
3. A demo page that renders every element in the baseline, with a theme toggle, a nested theme scope, an RTL section, and a wide table shown with and without the optional scroll wrapper. The theme toggle may use a few lines of inline JavaScript that the framework itself does not depend on.
4. A README covering:
   - How to link from the CDN and from npm. The CDN section shows two jsDelivr URLs:
     - A major-version link for most users, such as `https://cdn.jsdelivr.net/npm/barely-css@1/dist/barely.min.css`. It picks up fixes automatically. jsDelivr caches version-range URLs for a while, so a new release can take some time to appear.
     - An exact-version link with an `integrity` hash, such as `https://cdn.jsdelivr.net/npm/barely-css@1.0.0/dist/barely.min.css`, for users who want the file locked down. Subresource integrity only works with exact versions.

6. Automated checks, run with **Playwright** against the demo page:
   - **Tooling.** Playwright and `@axe-core/playwright` are maintainer-only dev dependencies. Users never install or run them, so the no-build-step rule still holds.
   - **Engines.** Every check runs in Chromium, Firefox, and WebKit. WebKit stands in for Safari in automation. Real Safari is still checked by hand before release.
   - **Accessibility scan.** axe runs on the demo page in both themes and must report no violations.
   - **Contrast check.** Every token pair listed under Color tokens is checked in both themes. A token change that drops any pair below its minimum fails the check.
   - **Layout checks.** The page is loaded at phone width (about 400px) and desktop width. It must never scroll horizontally, except for the documented wide-table case.
   - **`file://` check.** The demo page is also loaded over `file://` to confirm the downloaded-file path works.
   - **Screenshots.** The suite saves screenshots for each engine, theme, and width so changes can be reviewed visually. Whether to fail on screenshot differences is decided when building, because rendering differs slightly between machines.
   - **Dist freshness.** The suite also includes the check that both dist files are current with `src/` (see Deliverable 1).
