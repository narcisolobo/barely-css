# Ideas for a Modern Classless-First CSS Framework

## Guiding philosophy

The opportunity is not simply to make HTML look attractive without classes. It is to create a sensible, accessible, responsive design system that works with ordinary semantic HTML while leaving developers in control.

The framework should sit between browser defaults and component-heavy systems: polished defaults, a small surface area, and modern CSS doing the heavy lifting. Treat this as a modern rethink of classless CSS rather than a clone of any existing framework.

Three principles should guide every decision:

1. **HTML first.** Semantic HTML should be enough for a beautiful, usable baseline.
2. **CSS first.** No Sass requirement, JavaScript dependency, or mandatory build step.
3. **Customization first.** Developers should be able to adapt the system without fighting it.

A shared design system still matters even when markup is generated by AI or a framework: it provides consistency, accessibility defaults, maintainability, and predictable rendering.

## Modern CSS architecture

Use native CSS as the source of truth:

- CSS custom properties instead of preprocessor variables.
- Cascade layers for a predictable override model.
- `:where()` and `:is()` to keep selector specificity manageable.
- OKLCH color values for perceptually coherent palettes.
- CSS nesting where it improves readability.
- `color-scheme` so native browser controls follow the theme.
- Logical properties for writing-mode and RTL support.
- Modern selectors such as `:has()` where they meaningfully simplify styling.

A useful starting layer order is:

```css
@layer reset, tokens, base, layout, components, utilities, overrides;
```

Layering should let an application override framework styles without escalating selector specificity.

## Semantic HTML baseline

Ordinary HTML should look considered without classes. Cover typography, page structure, navigation, tables, media, forms, and native interactive elements.

| Category    | Elements to support                                           |
| ----------- | ------------------------------------------------------------- |
| Typography  | headings, paragraphs, lists, blockquotes                      |
| Structure   | `header`, `main`, `footer`, `section`, `article`, `aside`     |
| Navigation  | `nav`, links, breadcrumbs                                     |
| Tables      | `table`, `caption`, `thead`, `tbody`, `tfoot`                 |
| Forms       | `input`, `select`, `textarea`, `fieldset`, `label`            |
| Media       | `img`, `figure`, `figcaption`, `video`                        |
| Interactive | `button`, `details`, `summary`, `dialog`, `progress`, `meter` |

Avoid styling an element solely by its name when context changes its role. For example, an `article`'s `header` should not automatically look like the site's masthead. Use contextual selectors and restrained defaults.

## Forms

Forms are a major opportunity for a classless framework. Make all common controls coherent and usable: text inputs, native selects, checkboxes, radios, switches, range sliders, file and search inputs, and date/time inputs.

Account for disabled, read-only, required, invalid, focus, and validation-feedback states. Include helpful grouping and spacing, and keep focus indicators visible. Support native browser validation rather than introducing a competing validation system.

This should look polished without classes:

```html
<form>
  <label>
    Email address
    <input type="email" required>
  </label>

  <label>
    Password
    <input type="password" minlength="12" required>
  </label>

  <button type="submit">Create account</button>
</form>
```

## Design tokens

Make customization a first-class feature. Expose semantic tokens, not only raw palette values, and allow themes to be defined without recompiling.

| Token category | Examples                                            |
| -------------- | --------------------------------------------------- |
| Colors         | primary, secondary, surface, muted, danger, success |
| Typography     | font family, scale, weight, line height             |
| Spacing        | consistent spacing scale                            |
| Borders        | radius, width, color                                |
| Shadows        | elevation levels                                    |
| Layout         | content width, reading width, spacing               |
| Components     | button height, input height, card padding           |

For example:

```css
:root {
  --color-primary: oklch(55% 0.19 250);
  --color-background: oklch(99% 0.005 250);
  --color-surface: oklch(96% 0.01 250);
  --color-text: oklch(25% 0.02 250);
  --color-muted: oklch(50% 0.02 250);

  --radius-control: 0.4rem;
  --radius-card: 0.75rem;
  --spacing-unit: 0.25rem;
}
```

## Theming and dark mode

Dark mode should be built in rather than bolted on as a separate stylesheet. Support system preference, explicit light and dark modes, custom themes, and nested theme scopes.

```html
<html data-theme="dark">
```

A nested scope should also be possible, such as a light panel inside a dark application:

```html
<section data-theme="light">
  ...
</section>
```

Pair theme tokens with `color-scheme` so native controls match the surrounding surface.

## Responsive layout

Use modern layout capabilities instead of recreating a rigid Bootstrap-style grid. Prioritize fluid typography with `clamp()`, responsive spacing, container queries, Grid, Flexbox, intrinsic sizing, responsive images, and content-aware layouts.

A card collection can adapt to available space without breakpoint lists:

```css
.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 18rem), 1fr));
  gap: 1.5rem;
}
```

Offer a small optional class-light layout API for structures HTML semantics do not express well:

```html
<div class="container">
  <div class="grid">
    ...
  </div>
</div>
```

These classes are conveniences, not prerequisites.

## Native interactive components

Style native browser functionality well:

- `<details>` and `<summary>` for disclosures.
- `<dialog>` for modal dialogs.
- The Popover API for popovers and simple menus.
- Native form validation.
- `<progress>` and `<meter>`.
- Native focus, open, disabled, and other interaction states.

CSS should not imply behavior it cannot provide. Complex menus, tabs, and other widgets may still need JavaScript; the framework can style their native or authored behavior without pretending otherwise.

## Accessibility and progressive enhancement

Accessibility belongs in the foundation. Explicitly check keyboard navigation, screen-reader compatibility, visible focus, reduced motion, high-contrast and forced-colors modes, color contrast, zoom and text resizing, touch target sizes, and RTL layouts.

Do not communicate errors, success, or status through color alone. Favor semantic HTML and native browser behavior, and ensure content remains usable before optional enhancements load.

## Classless, class-light, and component layers

Do not force the framework to be strictly classless. Provide three clear layers:

### Semantic mode (default)

Pure HTML, with no classes needed for typography, forms, buttons, tables, or basic page structure.

```html
<main>
  <h1>Hello world</h1>
  <p>Welcome to my website.</p>
  <button>Get started</button>
</main>
```

### Class-light mode (optional)

A small set of structural classes for patterns that HTML semantics do not describe, such as containers and grids.

```html
<div class="container">
  <div class="grid">
    ...
  </div>
</div>
```

### Component mode (optional)

Explicit classes or data attributes for cards, badges, navigation layouts, and other deliberate UI patterns.

```html
<article class="card">
  <h2>Card title</h2>
  <p>Card content.</p>
</article>
```

This avoids forcing every conceivable interface pattern into semantic HTML while keeping the default experience classless.

## Developer experience and distribution

Make the first use simple and the deeper customization understandable:

- Zero runtime dependencies.
- CDN distribution as a drop-in stylesheet.
- An npm package for modern workflows.
- Native CSS source that is easy to inspect and customize.
- An optional compiler that can remove unused framework styles; the framework should remain usable without it.
- Examples that work with React, Vue, Svelte, Astro, and Next.js.
- A clear browser-support policy and documented fallbacks.
- Accessibility checks that help prevent regressions.
- A beautiful semantic HTML demo page that demonstrates the whole system.

## Things to avoid

- A JavaScript dependency for baseline styling.
- A mandatory build process.
- A proliferation of utility classes.
- An elaborate component library that obscures the HTML.
- An opinionated application architecture.
- Unnecessary abstractions around native HTML.
- CSS that imitates interactive behavior without implementing it.
- Styling that is difficult to override or customize.

The sweet spot is a framework that makes a simple website feel professionally designed while remaining almost invisible to the developer. Borrow the design-token discipline of larger systems, but keep the product close to the classless philosophy: semantic HTML, native CSS, and progressive enhancement.
